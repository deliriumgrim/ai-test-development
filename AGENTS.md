# AGENTS.md

Инструкции для AI-агентов, работающих с этим репозиторием.

## Структура

- Весь серверный код размещай только в `backend/` (Go), весь клиентский — только в `frontend/` (TypeScript + React, Vite).
- В корне находятся только `README.md`, `.gitignore`, `adr/` и служебные каталоги. Не добавляй в корень код или конфигурацию, относящуюся к отдельной части.
- Части самодостаточны: не вводи монорепо-тулинг (npm workspaces, Nx, go.work) и общую сборку через корень; сборка/запуск одной части не должна требовать другую.

## OpenSpec: SSOT и spec-driven development

Проект ведётся по подходу SDD (spec-driven development) с помощью OpenSpec (CLI: `openspec`).

- Единственный источник истины (SSOT) о поведении системы — спецификации в `openspec/specs/`.
- Любое изменение поведения начинай с нового change в `openspec/changes/` (артефакты: proposal → specs → design → tasks), а не с правки кода напрямую.
- Реализуй строго по `tasks.md` созданного change; после реализации change проверяют и архивируют — при архивации его дельты синхронизируются в основные спеки.
- Не редактируй `openspec/specs/` и `openspec/changes/archive/` напрямую: они меняются только через процесс OpenSpec.
- Если задача противоречит спекам — сначала предложи изменение спек (новый change), и только потом код.
- Сложную или неоднозначную задачу сначала прогоняй через исследовательский режим (`/opsx-explore`), затем заводи change (`/opsx-propose`).
- Новые capability-спеки размещай по частям: `specs/backend/<capability>/` — серверные, `specs/frontend/<capability>/` — клиентские, `specs/<общая-область>/` — сквозные (например, API-контракт). Конвенции артефактов (язык, объём, Gherkin-сценарии, acceptance-first, design review) — в `rules` файла `openspec/config.yaml`.
- Принятые ADR в `adr/` (`NNNN-kebab-title.md`) — обязательные архитектурные решения. Автоматически загружается только индекс `adr/README.md`; перед задачей, затрагивающей область существующих ADR, прочитай их из индекса (ориентир — поле «Область») и следуй им; при планировании change просматривай индекс целиком. ADR неизменяемы: пересмотр решения = новый ADR, заменяющий старый. При значимом архитектурном решении создавай новый ADR со следующим номером по шаблону из `adr/README.md`.

## Команды

Backend (выполнять из `backend/`):

- Сборка: `go build ./...` — должна проходить без ошибок после любых изменений.
- Запуск: `go run .` — порт берётся из переменной `PORT` (по умолчанию `8080`).
- Проверка работоспособности: `GET /healthz` → `200 OK`.

Frontend (выполнять из `frontend/`):

- Установка зависимостей: `npm install` (один раз).
- Dev-сервер: `npm run dev` → http://localhost:5173.
- Производственная сборка: `npm run build` (включает проверку типов `tsc -b`) — должна проходить без ошибок.

## Конвенции

- Backend: стандартная библиотека Go (`net/http`); не добавляй фреймворки и зависимости без необходимости.
- Frontend: держи минимальный набор зависимостей; не возвращай демо-контент из шаблонов.
- Артефакты сборки (бинарь `backend/backend`, `node_modules/`, `dist/`) не коммитятся — они уже в `.gitignore`.
- Топ-левел структура рассчитана на будущую смену стека: не привязывай соглашения структуры к конкретному фреймворку.

Подробности для людей — в `README.md`.
