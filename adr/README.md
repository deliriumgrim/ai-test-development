# Architecture Decision Records (ADR)

Каталог постоянных архитектурных решений проекта. Конвенции следуют схеме OpenSpec [`spec-driven-with-adr`](https://github.com/intent-driven-dev/openspec-schemas/tree/main/openspec/schemas/spec-driven-with-adr):

- Один файл — одно решение: `NNNN-kebab-title.md` (сквозная нумерация с `0001`).
- Принятые ADR **неизменяемы**: не редактируйте и не удаляйте их. Новое решение оформляется новым ADR, который в поле «Заменяет» ссылается на старый; старый остаётся без изменений.
- ADR фиксирует **решение и его обоснование (why)**. Авторитетное описание поведения системы (what) — в спецификациях `openspec/specs/` (SSOT).
- ADR обязательны к учёту во всех change-процессах OpenSpec и при любой реализации.

## Разделение по частям проекта

ADR ведутся **единым сквозным списком** — без подразделов `backend/` / `frontend/`:

- многие решения пересекают обе части (API-контракт, аутентификация, деплой) — подразделы вынудили бы дублировать или выгораживать «общее место»;
- единая нумерация даёт единую хронологию решений проекта;
- классические конвенции (adr.github.io, MADR) и схема `spec-driven-with-adr` исходят из одной папки; это же упрощает глобальную автозагрузку (`opencode.jsonc`).

Принадлежность решения фиксируется полем **«Область»** в метаданных ADR: `Бэкенд` / `Фронтенд` / `Общая`.

## Загрузка в контекст агента

Контекст не должен расти линейно с числом ADR, поэтому:

- автоматически загружается **снапшот индекса в `AGENTS.md`** (раздел «ADR: индекс»); ZCode, в отличие от opencode, не поддерживает автозагрузку произвольных файлов через конфиг (`instructions`), поэтому при добавлении ADR обновляй таблицу и в `adr/README.md`, и в `AGENTS.md`;
- сами ADR читаются **по необходимости**: перед задачей — ADR с совпадающей «Областью», при планировании change — все релевантные по индексу;
- основополагающие правила (например, «backend — Go») **дублируются в `AGENTS.md`**, чтобы критичные ограничения были видны всегда, а ADR хранит обоснование.

При росте индекса (>15–20 ADR): выводи устаревшие в статус «Заменён», объединяй тематические ADR; не поднимай автозагрузку отдельных ADR без острой необходимости.

## Шаблон

```markdown
# ADR-NNNN: <название решения>

- **Статус:** Принято | Заменён (ADR-XXXX)
- **Область:** Бэкенд | Фронтенд | Общая
- **Дата:** ГГГГ-ММ-ДД
- **Заменяет:** ADR-XXXX (или —)
- **Заменён:** ADR-XXXX (или —)

## Контекст

Какая проблема или ограничения привели к решению.

## Решение

Что именно решено; обязательные правила, если они есть.

## Последствия

Что становится проще, что сложнее; как решение отражается в спеках.
```
